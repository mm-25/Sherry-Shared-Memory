### F01 — Local capture history can cross Sherry account boundaries

This remains a serious final-product issue identified from the extension connection/status paths, but the user explicitly deferred the additional account-switching separation repair beyond the single-owner V1 on October 21. `background.js` retains profile-wide captures, `uploadExisting` can package them for a new workspace, and bridge status can expose retained raw history without its owner’s identity. Final-product work: repair account-bound storage, scoped status and connection/retry/export behavior in `extension/src/background.js`, `sherry-bridge.js`, `diagnostics.js` and their existing tests. Verify capture under A, sign-out, connection under B and return to A in one profile. B must receive neither A's content nor A's queued uploads. Q03/Q04 choose the local-only/retention presentation.

### F02 — A separate message with identical text can be discarded

This is P0 and was reproduced. `filterExactFallbackDuplicates` in `extension/src/core.js` drops a later no-provider-ID turn when its long text equals an earlier turn. The disposable probe supplied one distinct later message and retained none.

Replace content-only identity assumptions with proven turn identity/alignment. Test equal prompts and equal replies at separate positions, overlapping scans and streaming revisions. The new turn remains separate while a revision of a proven same turn updates once. A blind text-based cleanup of the real Gemini history is not an acceptable repair.


**October 24 implementation outcome:** The failing real-background-handler test now passes after removing the equal-text-only filter. Different turn identities with repeated long wording are kept, and observing the same identified turn again queues nothing. The obsolete core helper and its old loss-accepting test were removed. This correction is in staged browser source 0.4.23; the user's live check of that version remains pending. Ambiguous identity after a provider changes identifiers is still not solved by comparing text alone.

### F03 — Cloud sequence reconciliation can replace an unrelated message

Use a forward migration to remove or constrain the unsafe rule. Test a partially loaded conversation window that reuses sequence positions and a genuine identity improvement. Ambiguity must preserve records and evidence rather than overwrite text. Full-schema tests are required, not only the v1 ingestion path.


**October 24 implementation outcome:** CLI-generated forward migration 20261024203652_safe_capture_message_identity.sql removes the exact unsafe v2 rekey block. It is applied to Memory v1. A provider that changes all useful identifiers can still leave ambiguous copies; preserving evidence is the chosen behavior until the reader proves a match.

### F04 — HTTP success can remove an unconfirmed upload

This is P0 and comes from the extension and desktop upload paths. A response's HTTP status currently permits dequeuing without validating the expected immutable batch, committed state and complete event counts. A malformed success or lost-response retry can therefore look finished without enough evidence.

Repair `extension/src/background.js` and `desktop-capture/uploader.js` with the shared acknowledgement contract. Add success/mismatched ID/missing JSON/partial count/deletion-outcome fixtures alongside Android/import conformance. Unconfirmed delivery retains the exact request for retry.


**October 24 implementation outcome:** Browser and Mac use extension/src/upload-receipt.js as the same receipt rule. HTTP success must include ok=true, the submitted batch ID, result.status=committed, nonnegative integer counts and received=inserted+updated+duplicates=the submitted event count. Missing/malformed, wrong-ID, incomplete and uncommitted replies keep the unchanged payload for retry across restart. Real-handler regressions pass for both clients, and ordinary success fixtures now use the actual server response shape. These client corrections are staged in browser 0.4.23 and prepared Mac 0.1.1; user live validation remains. Shared Android/import conformance and every historical deletion-response variant are outside this completed client slice and remain explicit follow-up checks.

### F05 — Failed or offline work can lose its recoverable payload

This is P0 and comes from local retention/rejection/disconnect paths. The extension preserves rejected batch metadata but removes its full payload; bounded captured history and quarantine lists can remove the last retained text. Disconnect clears pending/rejected work without a chosen data-lifecycle policy.

Keep immutable failed payloads and their owner, separate preview retention from unsent retention, and stop new unsafe acceptance visibly at capacity. Test queue/history/rejection limits, restart, disconnect and local-write failures. Q04 determines customer choices; the implementation must not discard unsent information silently.

### F06 — Coverage can overstate what the reader observed

This is P1. `sync-core.js` defaults to a complete observed range without receiving enough unreadable-range evidence from the adapter/background path. The historical eight-area/four-readable result shows why an empty queue or a scan count is insufficient.

Carry observed range, candidates, readable turns, local durable commits and cloud confirmations independently. Default incomplete/unknown reading to partial. Verify that paired wrappers, unavailable offscreen text and unloaded history never produce an unqualified complete-chat claim.

### F07 — Credential filtering differs across save routes

This is P0. Captured cloud batches use `redaction.js`, while Personal Memory creation/update, MCP note writing and summary edits do not consistently use that policy. Browser local copies are also stored before cloud redaction.

Trace `backend/src/index.js`, `retrieval.js`, `memory-review.js` and every supported text write. Apply the chosen shared policy, test invented credentials through storage/search/export/archive and document local retention accurately. Audit existing real records separately rather than silently altering private content.

### F08 — An uncertain database response can remove a committed archive

This is P0 and comes from `backend/src/index.js`. A thrown metadata call deletes a newly created R2 archive even when the database may have committed before its response was lost. Ownership/cleanup failures can also leave orphan copies without adequate reconciliation.

Introduce ownership-first checks, immutable receipt/status resolution and durable cross-store recovery. Fault-inject database-commit-before-timeout, R2 failure and cleanup failure. Every committed transcript retains its accountable raw representation, and every uncommitted orphan has a safe scoped cleanup path.


**October 24 partial recovery outcome:** The deployed Worker checks ownership before writing an archive. A lost/malformed database reply, upstream timeout, throttling or server failure retains the immutable archive for retry. Only explicit transaction-rejection statuses are eligible for immediate removal of a newly created object. Tests prove a commit followed by a lost reply and identical replay leaves one archive and one logical batch. This repairs the identified destructive uncertainty path. It does not yet supply a separate durable reconciliation job for every abandoned, unindexed archive or resolve the historical orphan discovery question. Keep that remainder open before claiming the entire F08/deletion category finished.

### F09 — Import confirmation can hide shortened or changed text

This is P1. Claude normalization silently limits joined text to 250,000 characters, while current import readback checks identities/roles without full content/time/order integrity. A successful receipt can therefore overstate source preservation.

Repair `web/claude-import.js`, `import-integrity.js`, the web import flow and server readback. Reject or explicitly split long content, compare redacted digests and date/order evidence, and report exclusions. Test Unicode-heavy/oversized and interrupted imports, then official provider files.

### F10 — Gemini activity IDs and role labels can be unstable

This is P1. Current normalization can derive identity from export position and flatten activity text under a user role. A reordered or expanded export can reuse an identity for different content.

Use proven provider/account/record identity or hold uncertain matches. Verify real-format reordered/expanded fixtures and label activity according to what the archive contains. Q09 determines the customer scope; it must not promise complete exchanges absent from the source.
