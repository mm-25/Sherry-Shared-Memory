## What deleting one chat means

When the user deletes a conversation in Sherry, the Worker removes that conversation's messages and search records, deletes or rewrites the raw R2 archives that contain it, and records a tombstone for its workspace, provider, and provider conversation ID. Later extension scans or imports that submit **that same provider conversation ID** are ignored, so a deleted chat does not quietly reappear in Sherry. This is what “prevents recapture” means. A new provider conversation with a different ID is a separate source, even if its words are similar. The original chat in ChatGPT, Claude, or Gemini is not deleted by Sherry. Independent notes are not deleted just because a conversation is deleted; full workspace deletion is not implemented yet.

The earlier deletion path could leave historical derived claims behind because its conversation and checkpoint foreign keys use `SET NULL`. Nine source-less provisional rows from the retired claim feature had no conversation link, evidence row, or checkpoint reference. Two repeated the same Gemini-testing statement. The available database evidence does not prove which deletion, if any, caused each row to lose its source. With the user's explicit approval, migration `gate_9_delete_derived_claims` removed those nine rows on September 29 and added a trigger that removes claims linked to a conversation when it is deleted. Live verification found zero remaining cleanup candidates, one active deletion trigger, and all 1,882 claims still linked to existing conversations.
