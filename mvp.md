## 1. What Sherry does and who uses it

### 1.1 A shared memory across AI tools

Sherry is a personal memory service for people who use several large language models, or LLMs, across browsers, desktop applications and phones. An LLM is the AI behind services such as ChatGPT, Claude and Gemini. Today, useful context discussed in one service is difficult to carry into another. A person may explain a project in Claude, make a decision in ChatGPT, and later need Gemini to understand the same background. Sherry is intended to preserve that information in one account and make relevant parts available to the AI tool the person is currently using.

In this product, a **conversation** means the transcript of a person's interaction with a supported AI service: the messages the person wrote and the AI's visible responses. Sherry captures those exchanges in the existing provider interface. The initial product does not ingest interpersonal chats from messaging services. Adding another type of source needs its own approved integration and ownership rules.

Sherry is **LLM-agnostic** because the memory belongs to the person's Sherry account rather than one AI provider. It is **platform-agnostic in its target design** because compatible readers on different devices send the same kind of conversation records into that account. This does not mean one extension can read every application or that every AI host supports Sherry today. Each provider and device needs a tested integration; the implemented and missing integrations are described in section 5.

### 1.2 Information a person adds deliberately

A person can also give Sherry information without first discussing it with an LLM. For example, they might write a note saying that a project uses a particular measurement system, or save background they want future AI conversations to consider. In the current web app, these entries are created in **Personal Memory** using a category, field name and editable text. These are the person's own supplied records, not automatic conclusions about them.

An AI can save an explicit note through Sherry when the person authorizes that connection to write notes. That is a separate action from capturing a transcript. For example, the person can ask a connected AI to save a decision they have just made. Sherry must retain the note's origin so the person can distinguish information they entered directly from information saved through an AI. Q07 now accepts one Personal Memory destination for both origins, with labels and equivalent management actions; the current list still needs that implementation.

Attachments and other created artifacts are currently recorded only where references or metadata are exposed. Full documents, images and other artifact contents are a requested future direction, with storage and permission requirements still to define. The MVP must not imply that it has preserved a file merely because a message includes its filename.

### 1.3 Who retrieves the memory and who answers the person

Sherry provides the memory storage, search service and access controls. The LLM the person is chatting with produces the final answer. When that AI host supports the connection and chooses to use its tools, it sends Sherry a search request related to the current task. Sherry checks the account and permissions, searches that account's eligible records, and returns a bounded set of excerpts or notes with source information. The AI uses those results as context for its response.

An **authorized AI connection** therefore means a connection the person has approved to read their Sherry memory, and optionally to save explicit notes. It does not mean Sherry has permission to read all of that provider's account history. Capture permission, retrieval permission and note-writing permission are distinct capabilities.

The current connection uses **MCP**, a protocol through which an AI host can call tools such as search and source lookup. Connecting MCP alone neither guarantees that the host calls it on every question nor captures every exchange in that host. A supported capture reader supplies transcripts; MCP supplies permitted retrieval and explicit note writing.

### 1.4 What makes a memory useful

A useful result is one that helps with the person's present task and is supported by the stored source. Returning any matching sentence is insufficient. If the person asks for the final decision about a project, Sherry should find the relevant decision and any subsequent correction, rather than a similarly worded rejected idea. If the person asks for an exact date, a plausible summary without the original date is not enough.

Current retrieval uses database text search and can return source excerpts, explicit notes and retained summaries. It has not been demonstrated to retrieve the right memories consistently. The retrieval-quality gate will use actual tasks and known expected sources to compare exact-text search, metadata-aware ranking and any later semantic approach. We have not selected a replacement algorithm simply by pausing summarization.

Export, editing, access switches and deletion support this main promise: the person owns the memory that AI tools use. They are essential controls around the shared-memory experience, rather than the definition of the entire product.

## 2. The complete product loop

### 2.1 Connect a device to the person's Sherry account

The **main Sherry product** is the account-based memory experience: browsing transcripts, adding personal information, controlling AI access and managing data. The current implementation is a hosted web application. A **capture companion** is a smaller integration that reads supported conversations on a particular surface and sends them to that same Sherry account.

In a browser, the person opens the Sherry web app and installs the browser extension. The extension needs access to the supported provider pages and an authenticated connection to the person's Sherry account. The provider's own login allows its chat page to be displayed; Sherry's login determines which memory space receives captures. These two accounts must not be confused.

On macOS, the person uses the Sherry web app for the full memory experience and the desktop companion for supported native applications or coding tools. The companion connects to the same Sherry account, enables only selected sources and requests operating-system Accessibility permission where reading an application's visible text requires it. Windows has the same intended separation but no companion implementation yet.

On Android, the user now requires an installed main Sherry app as well as automatic capture. The person should be able to sign into the same account, find and inspect cloud memories, manage Personal Memory and AI/device permissions, and control phone capture from that app. The October 25 instruction expands the earlier companion-plus-responsive-web boundary. The existing Android code still implements only capture, queue and prototype Settings with developer workspace/token input; ordinary sign-in and the main-platform screens remain to build. The responsive website remains another way to access the same account. Q34 records the proposed first-version feature depth; this paragraph establishes the mobile product requirement without claiming that the proposed screen set or implementation is already approved or complete.

The current V1 test uses one Sherry owner across the selected devices. On October 21 the user explicitly deferred shared-profile account switching and local person-A/person-B separation to the final product. Continue using the intended account and existing server authentication/ownership checks. V1 does not claim safe switching between different Sherry owners in the same browser profile; the additional local partition/onboarding repair remains required before that broader use is supported.

### 2.2 Capture ongoing conversations

After permission and source selection, the companion watches the supported conversation interface while the person continues using their AI tool. The browser reader examines the provider's page elements. Native readers use exposed Accessibility text or structured conversation logs where available. They identify user and assistant turns, preserve exposed source IDs and dates, and save readable content locally before attempting cloud delivery.

The browser reader must start and continue with its popup closed. Opening the extension should let the person inspect or control capture; it must not be the action that makes ordinary capture begin. Automatic saving is an expected integration behavior, not a special product feature invented to excuse the current startup failure.

The cloud service does not independently scrape the person's signed-in provider accounts. It receives the observations sent by authorized companions, validates them, applies the storage rules, and stores the eligible messages. If a provider has not exposed older messages, the companion cannot honestly claim those messages have been captured.

Captures should upload promptly without intervention. A short-lived durable buffer on the companion protects messages already read until Sherry confirms receiving them. For example, Gemini can display a completed reply while Sherry's separate service is unavailable, or the browser can close before an upload finishes. This is delivery protection; it does not imply continued use of a cloud LLM while offline or require a permanent full transcript archive on the device.

There are three distinct facts during capture. First, the reader may find a message container on a ChatGPT, Claude or Gemini page without being able to read its text. Second, it may successfully save that text on the computer or phone running the companion. Third, the cloud may confirm that the expected message is stored in the person's Sherry account. These distinctions belong in capture status and recovery explanations. They are not proof that the entire account's history is complete.

### 2.3 Import existing history or intentionally selected information

Ongoing capture mainly observes conversations opened in supported interfaces. To bring older history into Sherry, the person can obtain an official export from the AI provider and import its supported contents. The web app reads the selected file, identifies eligible conversation records, and sends normalized messages through the same cloud ingestion service used by capture.

The current web importer expects extracted JSON files and limited Gemini activity HTML; it does not accept every provider ZIP as a complete archive automatically. The product needs provider-specific instructions explaining what file to choose and what the archive contains. A Gemini activity archive may not provide complete alternating conversations, so its limitations must be stated before importing.

An import should explain how many chats and messages will be added, how much overlaps existing memory, which records are excluded and which matches need review. The person can skip history import during connection and add it later. The result must account for eligible records and explain any incomplete upload instead of presenting a general success message. A repeated import should leave previously stored messages unchanged unless a proven revision needs updating.

The latest V1 deletion decision allows a deleted source to be collected or imported again through ordinary capture/import. Deletion removes the currently stored Sherry copy; it does not permanently exclude the original provider chat. Section 3.4 and Q20 record this superseding decision and distinguish it from what the live code still does.

### 2.4 Inspect and organize what was saved

**Inspection by the person** means opening Sherry to see the actual stored transcript or supplied note. They should be able to read the messages, see who said them, understand the source and dates, and recognize whether some history is missing. Inspection is optional in ordinary use; the person should not have to compare every chat manually to make capture reliable.

**Verification by Sherry's system** means checking the delivery receipt, identities and coverage evidence in the background. A count shown by the extension is not sufficient. The server and companion must be able to account for which observed turns were committed, whether an attempted retry created a copy, and whether a range is unreadable or unavailable. The plan defines those acceptance checks.

Organization must help someone recognize information without requiring them to remember the project or exact phrase in advance. Categories are useful for deliberately entered information; source/provider/date filters help with transcripts. Projects are accepted as optional organization under Q15; they do not enforce an AI-access boundary.

### 2.5 Retrieve context in another AI conversation

The person connects an AI host to Sherry and grants read permission. When that host asks for context, Sherry searches only the connected person's allowed records and returns source-backed information within the context limit. A relevant ChatGPT conversation may therefore supply context to Claude, or vice versa, when those integrations are supported and enabled.

The person needs to know which AI tool can read memory and whether it can save notes. Turning a category or provider permission off must affect later search and direct source lookup. Sherry cannot remove information already delivered into a provider's earlier conversation; that boundary must be explained when access is revoked.

### 2.6 Correct, withhold, export or remove information

A person can correct an explicit note, choose which stored categories may be supplied to AI tools, export the agreed scope of their memory and delete Sherry records. Turning access off leaves the information stored for the person to inspect; deleting it removes it according to the defined deletion scope.

Source transcripts remain evidence of what was captured. Editing a Personal Memory note or a generated summary must not silently rewrite the provider's original messages. Removing a chat from Sherry leaves the provider's original conversation unchanged. Deletion may have to finish across several cloud stores and offline devices, so the product must report progress accurately.

## 3. Categorized product decisions and their reasoning

### 3.1 Product structure and presentation

The account-based web app is the current full memory-management surface. Extensions and native companions provide immediate capture controls without recreating the whole product beside every AI chat. This separation keeps one set of stored data and settings while allowing each platform to use its appropriate reading method. A person should see the same memory after signing into Sherry from a different supported device.

The production interface uses compact navigation, clear hierarchy, white/light surfaces, readable sans-serif typography and Sherry's violet accent. Provider labels, source dates and task-level states must be understandable without developer knowledge. Search and filters are contextual to the area being viewed; they must not secretly change a person's AI permissions.

The current **Diagnostics** destination is a development/testing tool, not an approved destination in the final customer navigation. Customer-facing problems still need understandable guidance where they occur, such as a disconnected companion or partial import. The technical diagnostic console should support development/support without forcing customers to interpret batch IDs or database failures. Q21 accepts contextual customer status and a Settings device/status area, with a separate deliberate developer/support diagnostic boundary.

### 3.2 Information collection and identity

Sherry should preserve eligible user and visible assistant turns, their order, exposed conversation/message identity and original dates when available. The date the companion observed a message is a separate fact. An old Claude chat imported today must not appear to have originally happened today merely because Sherry received it today.

Reading the same turn twice should not create two stored messages. However, two separate turns with identical wording must remain separate. Cross-device reconciliation should rely on proven provider/account/chat identity rather than assumptions based on text. These rules are essential because the same conversation can be opened in a browser, a native app and an export.

Temporary/private conversation capture is excluded by default in the browser extension. A broader temporary-chat promise cannot be made for native readers until they can detect that state. Full artifact contents, hidden reasoning and unavailable provider history are not implied by transcript capture.

### 3.3 Storage and access control

Capture permission determines whether a companion collects supported conversation information. Provider read permission determines whether a connected AI can receive information already stored in Sherry. Explicit-note write permission determines whether that AI can save a requested note. Each control needs an independent and understandable effect.

Financial, Health and Personal switches are retrieval controls. If Financial is turned off, eligible financial information stays in Sherry for the owner but is withheld from connected AI requests. The simple Settings copy should say: **“When this is off, your AI tools cannot access this information from Sherry.”** Q06 accepts withholding an uncertain mixed chat as a whole until eligible passages can be separated safely, with optional manual labels; automatic detection must not be presented as perfect.

Credentials such as passwords or API keys need consistent handling across captured transcripts, directly entered notes, AI-written notes and edited summaries. The current cloud capture filter does not cover every write path, and browser local copies are retained before cloud filtering. That incomplete enforcement is a release defect, not an approved difference between ways of saving information.

### 3.4 V1 deletion removes the stored copy and permits later recapture

The latest October 21 user decision disables the permanent rule that prevents a deleted chat from being captured or imported again. For V1, deleting a chat means removing the transcript and its associated Sherry search entries, summaries and raw archive copies. The original ChatGPT, Claude, Gemini or other provider conversation remains at that provider. Personal Memory notes, account settings and AI connections are outside a chat-only deletion.

If capture is enabled and later reads that original source again, eligible messages may return to Sherry. An ordinary supported import may also add the source again. This is new ingestion from an available source, not recovery of Sherry bytes already erased. The wording must tell the person that deletion does not turn capture off or permanently exclude a chat. To keep a testing library empty, pause the relevant companions and close old provider chats before the wipe; resume only on the named test conversations afterward. Existing waiting uploads can otherwise refill it.

The earlier accepted Q20 design combined a permanent deletion block with a separate add-and-resume action. That design is superseded for V1; its earlier decision remains visibly recorded in Questions. There is no requirement to build that restoration screen before this reset. A separate final-product source-exclusion design would need a later decision rather than being silently reintroduced.

The coordinated change is now deployed. A deletion record tracks cleanup and identifies that deletion operation; it no longer permanently bans a completed source. Uploads arriving while cleanup is unfinished receive a retryable response so the companion retains them. After cleanup finishes, ordinary capture/import is eligible again. Cleanup records retain a frozen list of older archive copies, and recaptured archives use a separate operation-derived location. Live database tests passed for recapture, pending cleanup, stale work and a second deletion; those invented records were rolled back. Full browser/provider replay and the real library wipe remain separate checks, not results implied by this database test.

Whole-account deletion is separate from restoring one source chat. It removes the account and workspace and does not imply an undo facility. Export scope, provider-wide deletion and any future account restore remain distinct decisions.

### 3.5 Retrieval strategy and retired generated facts

Automatic summarization was paused because you questioned whether compressing conversations is the most efficient and precise way to retrieve useful information. A summary can omit exact wording, exceptions, corrections or details that later matter. The paid summarization path also had an invalid-key retry problem. That implementation history does not settle the product question; the primary reason for deferral is to evaluate a better retrieval method against source-backed tasks.

Existing summaries remain stored as optional labeled reading aids under Q08. Their future retrieval role is decided by evaluation rather than by this approval. No replacement provider key or resumed automatic model spending is required to finish capture. A summary-assisted candidate may be compared later, but it is not the chosen architecture for memory usefulness.

Automatic extracted claims and conflict review were retired because they produced unsupported or low-value conclusions and comparisons that did not help the person's task. The interface required people to approve trivial inferred facts and treated some restatements or unrelated contexts as conflicts. Explicit information and original source evidence are a stronger present foundation. New cross-chat contradiction handling needs a separate evaluation rather than reactivating the old machinery.

## 6. User journeys and edge cases

### Journey 1 — Join Sherry and connect a first device

The intended journey begins with entering the person's own Sherry account, connecting one supported capture device and granting source access. A short checklist should explain the actual browser/app steps, offer defaults and make history import optional. The first-use success condition is a real user/assistant exchange confirmed in that account, not an installed icon.

If invitation verification is incomplete, sign-in fails, an account already exists or a password has been forgotten, the person needs the appropriate recovery route without accidentally creating another workspace. If permission is declined, setup remains incomplete and explains what still works. If another account's unsent captures remain on the device, those captures stay with their owner and are not silently uploaded. Q03, Q12 and Q13 define unresolved first-use details.

### Journey 2 — Continue chatting with automatic capture

The person continues in a supported AI interface with capture enabled. The reader saves both sides once content is readable and sufficiently settled, without needing the popup. A revised streaming response should update its own message rather than produce a separate answer for every intermediate rendering.

New chats without a permanent URL, first-turn loading, provider navigation without reload, offscreen content, empty message wrappers and regenerated/edited answers must be handled explicitly. If a turn cannot be read or its identity is ambiguous, preserve available evidence and show a partial state instead of inventing success. Pausing or revoking permission stops new observation; the contract for an upload already in flight is specified separately.

### Journey 3 — Import older history

The person follows provider-specific export guidance, chooses a supported file, reviews the import scope and starts it. Sherry accounts for newly added, existing, excluded, deleted-source and unresolved records and lets the person inspect imported transcripts and original dates.

Malformed files, unsupported archive types, non-text-only chats, alternate branches, oversized text, interrupted upload and changed/reordered exports need distinct outcomes. Sherry must not silently shorten a message or turn a missing date into today's date. Repeating an import should not create copies. An interrupted import should retain progress for a safe retry; provider-specific deletion is a separate control, not an assumed import-undo feature.

### Journey 4 — Find and inspect a transcript

The person uses title/content search and source/device/date filters, opens the transcript and optionally follows its original provider link. They can read in either chronological direction and optionally locate the selected chat in Connected Conversations.

No results, partially loaded search data, an unknown original timestamp, a deleted/inaccessible source link and a partial transcript must be distinguishable. A private provider URL helps locate a chat but does not grant Sherry's server the ability to fetch it. A map connection needs an explanation of its basis; unavailable generated topics should not cause a misleading relationship claim.

### Journey 5 — Understand generated summaries, if retained

Existing summaries can currently be viewed, corrected or removed while the source transcript remains. Future visibility and retrieval use remain under review because exact information can be lost through compression.

A missing, stale, failed or source-partial summary is not equivalent to missing transcript storage. Paid processing should not repeat unchanged failures. The person should not be forced through developer version-history workflows or supply a model key to make capture usable. Q08 owns the summary decision; this journey does not authorize automatic summarization to resume.

### Journey 6 — Supply and manage explicit information

The person adds a category/field and information directly, or explicitly asks a permitted AI to save a note. They should be able to inspect origin, edit the supplied record and remove it without changing a source transcript.

Empty/oversized input, a save response that was lost, repeated submissions, a credential pasted into text, a deleted category, conflicting explicit notes and AI write permission denial need clear outcomes. The current UI cannot manage every AI-origin note; Q07 settles one origin-labeled Personal Memory view; its implementation still needs verification. Sherry must not resolve conflicting notes by inventing an authoritative preference.

### Journey 7 — Ask an AI to use prior information

The person approves an AI connection, asks a task-related question and receives an answer informed by permitted Sherry results when the host invokes its tools. Source references should allow the person or host to inspect the supporting record.

An unconnected host, revoked token, disabled category/provider, no useful result, ambiguous matches, a newer correction and truncated context require explicit behavior. A wrong-account request must be denied. Sherry should return no supported memory when the evidence does not support one; a fluent final answer is not proof of correct retrieval.

### Journey 8 — Export, delete or deliberately add a source back

The person chooses export or a clearly scoped deletion: one chat, selected chats, provider data when implemented, or the whole Sherry account. The result names what was processed and whether cleanup remains pending. A future deliberate source-restoration action will be distinct from automatic recapture.

During export, new captures can arrive; Sherry needs a defined snapshot boundary and must include every record type promised by the action. During deletion, some cloud stores or devices can be offline; retries must not affect unrelated chats or newly recaptured copies. The latest V1 policy permits ordinary future recapture, so an active old tab or surviving upload can repopulate a deleted source. A clean testing reset therefore requires capture to be paused and existing waiting work accounted for before clearing the cloud library. Whole-account erasure remains separate and is not an undo operation. Q05, Q10, Q11 and Q20 own those boundaries.

### Journey 9 — Recover from a capture or account problem

The customer receives a short explanation in the affected task: what stopped, what is still saved, and the next action. Developer/support diagnostics provide technical detail separately when needed.

Expired sign-in, unavailable cloud, lost permission, rejected payload, full local storage and damaged encrypted state are different failures. Reconnecting should resume the same account's preserved work. Repairing one chat must not resend every unrelated chat, and clearing a warning must not discard the last recoverable message copy. Background checks should detect incomplete delivery rather than requiring the person to count every transcript themselves.

### Journey 10 — Add another source or device

The person connects a supported second device or provider to the same Sherry account and can browse the same cloud memory there. Future extra provider accounts and sources require explicit namespace and permission rules.

Two devices observing the same chat, switching Sherry owners on a shared device, revoking a lost device, changing provider accounts and unsupported application versions need safe behavior. New integrations such as Perplexity, Obsidian or NotebookLM cannot be declared supported simply because they expose text. Full artifacts and project-specific access need defined ownership, storage and retrieval contracts before activation.

### 12.2 What the person should be able to influence

Retrieval starts from a question and selects permitted evidence before the LLM answers. A **hard filter** excludes evidence completely; a **soft preference** changes ranking among eligible evidence. Account ownership, deletion and disabled-category rules are hard eligibility conditions and cannot be weakened by visual preferences.

A time-emphasis control could prefer recent eligible decisions or allow older context to compete, while still keeping task relevance important. ## 26. Source information and reliable delivery update — October 30

This implementation pass makes recorded information mean the same thing across the supported clients without pretending that every AI app exposes the same facts. Source metadata means information about where a captured fact came from. A source title is a title actually exposed by the provider; a derived title is built from message text; a generic title is a placeholder. A source date is an actual message timestamp; a session fallback is a session-level date that cannot establish when that message was sent; an observed date describes when Sherry read the message. Unknown remains a valid state. Earlier records are not retrospectively labelled as proven original information.

The new browser reader identifies these distinctions for ChatGPT, Claude and Gemini. It can send a changed title for a known conversation even when no new message has been written.
