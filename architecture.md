## 1. System responsibilities and the complete data flow

### 1.1 Main product and capture companions

The main product is the account-based Sherry memory experience, currently implemented in the hosted web app. A customer can browse stored AI transcripts, supply their own information, control access by connected AI tools and manage stored data. The web app is usable in a browser on different screen sizes; a complete native mobile memory library has not been implemented or selected as the only management surface.

Capture companions collect eligible information where the customer already works. The browser extension reads supported provider pages. The macOS app reads exposed native chat or structured coding-tool logs. The Android prototype reads an explicitly permitted supported application or accepts shared/pasted excerpts. Windows needs a separate implementation. These clients share a cloud contract but do not share every extraction method or permission mechanism.

The data route is: a reader observes a supported turn; the client saves the observed content and delivery work durably; an authenticated request sends a batch to the Cloudflare Worker; the Worker validates ownership/content, filters deleted sources and recognized secrets, coordinates archive/database storage, and returns a receipt; the web product reads stored records from the account-scoped service. An AI host later calls the MCP service to search or inspect permitted records.

The cloud does not scrape the customer's signed-in AI accounts independently. Capture requires the local/provider integration to expose and send eligible messages. An MCP connection does not supply every chat transcript unless its host deliberately calls a write operation with that content. These boundaries prevent a connected search tool from being mistaken for comprehensive capture.

### 1.2 Cloud services and configuration

The Cloudflare Worker serves the web assets and handles capture, browsing, settings, explicit notes, diagnostics and data deletion. `backend/src/index.js` is the application handler; `worker-entry.js` wraps the MCP/OAuth service. Scheduled work runs every five minutes according to `backend/wrangler.jsonc`.

Supabase provides account authentication and the Postgres database. The configured project is `zwpzmmfpgjaaikacoqas`. Cloudflare R2 stores redacted capture envelopes in bucket `shared-memory-raw`; OAuth connector state uses the `OAUTH_KV` binding. The configured Worker origin is `https://shared-memory-ingestion.mufaddal-m25.workers.dev`. These identifiers describe the configured destination; they do not certify that the latest local changes have been deployed there.

The database holds chat/message identity, searchable text, notes, permissions, receipt/provenance information and background-work records. R2 preserves the redacted original batch representation. A raw batch is not automatically the authoritative full provider transcript: it represents the eligible content that a particular capture/import operation observed.

### 1.3 Source ownership and code boundaries

The extension's `core.js` owns normalization and fallback identity helpers. Provider adapters identify readable elements and exposed metadata. `web-provider-adapter.js` supplies the common Claude/Gemini observation loop; the ChatGPT adapter retains its own runtime. `background.js` owns local mutations and upload processing, `sync-core.js` constructs payloads, and `tab-recovery.js` restores readers after startup/navigation. `popup.*`, `diagnostics.*` and `sherry-bridge.js` expose control/status paths.

The backend's `validation.js` defines accepted envelopes and limits; `redaction.js` handles recognized secrets; `retrieval.js`, `mcp.js` and `oauth.js` implement AI access; `account-deletion.js` processes durable cleanup. Summary scheduling, checkpoints, gateway normalization, cost estimates and encrypted settings live in their respective backend modules. Database behavior is the whole ordered migration history under `backend/supabase/migrations`, not one selected function file.

The current web app puts many flows in `web/app.js`, with separate helpers for import integrity, Claude matching, transcript ordering and graph connections. Any refactor should follow the affected flow's tests and separate responsibilities that genuinely need independent verification. Replacing the entire application is not required to repair the capture loop.

Desktop capture uses `service.js`, source parsers/collectors, `batches.js`, `state.js` and `uploader.js`; native Accessibility is implemented in `macos/ax_snapshot.m` and the packaged app bridge. Android separates pure capture/session logic in `core` from the Accessibility service, encrypted store, UI and WorkManager uploader in `app`.

## 2. Identity, sessions and access boundaries

### 2.1 Sherry ownership versus provider identity

The Sherry account owns a private workspace. The workspace ID must accompany every stored-data operation, but receiving an ID from a client is not proof that the signed-in person owns it. The server must authenticate the person and verify ownership before reading or changing records. Related records, such as a note's optional project, must belong to that same workspace.

A provider account is a different identity. A customer may eventually have two ChatGPT accounts within one Sherry workspace. The current model lacks a complete provider-account namespace; that expansion remains Q14. Similarly, a capture device ID is provenance, not proof that the device is authorized. Device registration/revocation needs a separate credential/session design before customer-facing management can rely on it.

The browser's current local history is not fully partitioned by owner. Reconnecting with `uploadExisting` can assign retained captures to the next workspace, and the status bridge can expose raw retained events without account ownership. The latest October 21 user instruction explicitly defers this F01/E21 shared-profile separation work beyond the single-owner V1. V1 testing keeps one intended Sherry owner and does not claim safe owner switching. Preserve current cloud authentication/ownership enforcement. Before final-product multi-owner use, bind pending and retained content to its owner and constrain signed-out/differently signed-in status/control access.

### 2.2 Authentication and secrets

Capture/web requests currently use the customer's Supabase session access token. Public clients may receive the publishable Supabase configuration, but database admin credentials and the settings encryption secret must remain in Worker secret configuration. A browser origin allow-list or CORS permission limits caller surfaces; it does not replace account authorization.

For a customer-ready connection, use ordinary sign-in and supported session refresh rather than copying access tokens. Supabase sessions involve access and refresh credentials; the session behavior and revocation implementation must be checked against its current documentation before implementation. [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions).

The intended customer experience stays signed in through normal use, browser restart and routine access-credential expiration. Renew short-lived credentials automatically; request manual authentication only for explicit sign-out/revocation, a genuinely invalid session or a separately selected security policy. Supabase supports long-lived sessions with refreshed credentials. Q25 now explicitly selects no routine forced logout for the first release. [Supabase session lifetime documentation](https://supabase.com/docs/guides/auth/sessions).

The present web/extension refresh paths react to an unauthorized response; the desktop path checks expiry in advance. Android's developer-token prototype has no ordinary refresh. Transient refresh-service/network failure must be distinguished from invalid authentication, with retained delivery work and retry instead of unnecessary manual sign-in. Cross-client refresh ownership and rotation require tests; these paths are not live reliability proof.

Web-dashboard sign-out and explicit capture pause have separate effects. The target leaves independently authenticated companions running when the web dashboard is closed or signed out; each companion's genuine credential revocation stops that connection's privileged delivery. An account-wide pause setting must be synchronized to affected devices with an applied/pending state. Current client-local controls are not that complete synchronization mechanism.

Signing out, deleting an account or changing a permission must be verified against requests made with already-issued credentials. A token's apparent structure or expiry is insufficient for immediate revocation guarantees. Sensitive operations need current ownership/session/connection checks; Q12 and E13 cover the exact lifecycle and live proof.

### 2.3 Database protection and privileged paths

Row-level security, or RLS, limits which database rows a role can access. Table grants decide which operations that role can perform at all. Both matter. Server admin/service credentials bypass RLS, so application ownership checks and relationship constraints are still required. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

The October 7 disposable replay applied all 33 migrations with an Auth stub and the unavailable `pgcrypto` declaration omitted. All 27 public tables had RLS, and no public security-definer function was executable by anon/authenticated in that replay. This was local schema evidence, not a current live Supabase security-advisor/Auth test. F12 showed that a note could still reference another workspace's project, illustrating why table-level ownership alone does not establish relationship integrity.

Untrusted source text, import files, metadata and generated text must remain data. Web rendering generally uses text nodes/React rather than interpreting source content as HTML. Any HTML template interpolation still needs review against the actual inputs. Logs and troubleshooting exports should default to counts, IDs and error categories rather than raw transcripts or credentials.

## 3. Capture clients and local durability

### 3.1 Browser permission and startup contract

The extension needs permission to run on each supported provider origin and access its Sherry cloud/auth destination. Persistent site access differs from a one-click active-tab grant. Installation, update, browser restart, opening a previously existing provider tab and in-page navigation must start or resume the reader without a popup action.

Chromium background service workers can stop during inactivity and wake on events. Global variables disappear, so persistent state and registered wake/retry handlers must survive termination. [Chrome lifecycle documentation](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle). Firefox uses background scripts rather than Chromium's worker implementation, requiring compatible manifests and recovery behavior. [MDN background documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

There is no fixed thirty-second user wait that establishes success. A loaded message change should be observed, settled and saved promptly; a five-second scan provides a fallback for missed changes. A separate upload alarm recovers sleeping/background delivery. Their actual timing must be measured on the supported browser, especially with a background tab or throttled network.

Permission denial/revocation must stop new reads and leave a clear disabled state. Checking status must not itself trigger the only scan and then make a broken startup look functional. G3 tests the reader with the popup closed and uses passive stage evidence.

### 3.2 Page reading and message extraction

The browser reader uses the DOM, the structured elements rendered by the provider. It watches element/text changes, waits for responses to settle, identifies the conversation and roles, and periodically rereads the loaded chat. It does not hook arbitrary provider scripts or claim access to private network history.

Each provider adapter must identify actual message content containers and exclude composer text, controls, loading/status labels and hidden alternate UI. It should preserve readable lists, paragraphs and code formatting. Missing text, unknown roles or incomplete elements produce an observation gap, not an invented message. A wrapper containing both sides of an exchange must not be counted as one readable turn or double-counted as two turns without extraction evidence.

Gemini's offscreen rendering can retain text while `innerText` is empty. The local candidate temporarily changes the message's rendering optimization, reads formatted text, restores the original styles and filters known controls. It is more constrained than copying all `textContent`. Current real Zen acceptance remains open; local fixtures do not prove the provider's present layout.

Older history that has not been loaded into accessible page elements remains unavailable to the reader. Q02 now accepts capture of every eligible readable loaded turn, with truthful partial-history status and official import for additional history. Automatic scrolling or undocumented provider fetching is not an approved replacement contract.

### 3.3 Stable turn identity and revision

A message's **identity** distinguishes one actual turn from another. Its **content digest** compares text versions. Two turns can have equal digests and still be distinct messages. Prefer exposed provider message IDs; otherwise use persistent local observation identity with proven ordered alignment. The server must include workspace, provider/account namespace and conversation identity in reconciliation.

The reviewed baseline fallback helpers use position/role and FNV32 fingerprints. F02 reproduced a local filter dropping a distinct identical long turn; F03 reproduced cloud replacement of a different turn at the same observed position. The October 24 corrections and remaining identity limitations are recorded in section 19. Position numbers can restart when the provider exposes only a later window of the conversation.

Streaming revisions should update a proven same turn. New chats without a permanent URL should retain their first turns under a provisional identity until rekeying is proven. Regenerated/branched/edited content without durable identity must preserve uncertainty rather than overwrite earlier evidence. Changing the identity algorithm also requires a migration/reconciliation strategy that does not corrupt already stored chats.

### 3.4 Extension storage today and required changes

The extension uses `storage.local` for raw events, immutable upload payloads, tokens and diagnostics, and `storage.sync` for boolean settings. There is no application-level local encryption. Current bounds retain 2,000 captured events, 100 queued batches, 50 rejected-batch metadata entries and 500 diagnostics. Temporary-chat and attachment capture default off; general capture defaults on.

The current rejected-upload path removes the pending payload and keeps metadata only. Later local-history trimming can remove the remaining text copy. Disconnect also clears queued/rejected work while retained raw history remains. F05 requires full immutable rejected payload retention and visible capacity handling. A full queue must prevent unsafe new acceptance without silently evicting unsent data.

The reader must receive a local-save acknowledgement only after the event and its upload work are both durable. If that write fails, it must not advance its saved cursor. Account switch, restart, update and storage failure tests must verify the same invariant. Q03/Q04 now require account connection before collection, owner-bound waiting work and minimal confirmed-payload retention; the implementation cannot silently move it to another owner.

The device upload buffer protects observed messages between reading and confirmed cloud commit. The person need not be able to chat offline for this to matter: a provider reply can be available while Sherry's service is temporarily unreachable, or the browser can close after reading but before confirmation. Send promptly and retry automatically. The accepted minimal-retention design removes confirmed payload text when safe while keeping the identity evidence needed for reconciliation; today's retained recent-history store is broader than that proposal. Q04 governs deliberately removing unsent work, not routine hourly login interruptions.

### 3.5 macOS implementation and completion contract

The macOS app communicates with its Node service through private inherited pipes. In-process Accessibility snapshots read only positively identified allow-listed applications. Codex and Antigravity prefer structured local logs; Claude reads exposed ordinary chat. Claude Code parser/tests remain retained but inactive in the current service. Windows is not implemented.

The state file uses AES-256-GCM with a Keychain key, atomic replacement, a single-writer lock and one-workspace binding. Recent preview records are bounded to fifty turns or two MiB per source. Durable pending/rejected payloads need their own retention/capacity checks; a preview bound cannot silently discard unsent work. Account tokens refresh through the existing desktop connection path, but the uploader still needs strict acknowledgement validation.

Claude historical capture worked when its ordinary chat was exposed. Background visibility, source edits, long log failures and browser/import reconciliation remain open. Native ChatGPT is disabled because earlier “ChatGPT” records were Codex content in a shared app view. A positive source discriminator is required before enabling it, and historical mislabels need a scoped audit before any real-data repair.

Ad hoc app re-signing can change the Accessibility permission identity. A customer release needs a stable signed distribution/update path and exact permission-owner validation. Preserve the working installed app while preparing a candidate; do not repeatedly invalidate the customer's grant during exploratory builds.

### 3.6 Android implementation and completion contract

The Android prototype uses Kotlin/Compose, an Accessibility service, an encrypted local store and WorkManager delivery. It defaults paused with no account connection/source enabled. Shared or pasted information needs explicit save. Requested ChatGPT reads provide a settled preview; automatic capture has a separate opt-in.

The parser accepts the observed English ChatGPT 1.2026.265 layout. Unknown versions, active generation controls, password/editable fields and uncertain message structure should stop acceptance rather than be read indiscriminately. The declaration currently names ChatGPT, Gemini and Claude, while only one automatic reader exists; access declarations must match implemented/enabled sources.

Local session reconciliation uses a unique ordered overlap of at least two distinct unclipped anchors. Ambiguous/repeated patterns and edits stop joining. Original provider dates/message IDs remain unknown; coverage remains partial and clipped bounds carry warnings. A user choice to continue or start a separate capture is evidence, not a canonical provider ID.

AES-GCM/Keystore storage is atomically replaced, excluded from backup/device transfer, and protected by a secure-window flag. The queue holds up to one hundred captures or ten MB with sixty-thousand-character excerpts. The registry is bounded to one hundred sessions and one thousand turns per session without silent eviction. Frozen requests remain bound to their workspace. Current developer token input has no ordinary sign-in/refresh; real-device automatic/private-chat/switching tests remain.

Evidence-bearing requests require server capability `captureEvidenceVersion: 1` and the corresponding October 2 migration/Worker changes. Those local changes must be confirmed deployed before a client release can depend on them. Removing evidence to make an old server accept a request would misrepresent the native observations.

## 4. Cloud ingestion and confirmation

### 4.1 Request shape and limits

Clients POST JSON to `/v1/capture/batches` using their user-session credential. Each immutable request has a UUID `batchId`; the idempotency header identifies the same batch. Schema v1 remains supported; v2 includes source/client/coverage evidence. Retrying uncertain delivery uses identical payload bytes and the same batch ID. Editing a batch in place during retry breaks that contract.

The envelope identifies `workspaceId`, `provider`, `reason`, `clientCreatedAt` and its `events`. In v2, `providerFamily` groups OpenAI/Anthropic/Google; `product` matches the provider product; `surface` identifies web, desktop, CLI, IDE or Android. `captureClient` identifies adapter type/version, device, OS, optional app version and capture session. These fields describe provenance, not permission.

Each event identifies its conversation, event ID, exposed provider-message ID when available, role, sequence, text and digest. `messageTimestamp` records the original source time or null; `capturedAt` records the observation time. A provider URL or local source locator explains origin. Title, HTTPS links and permitted attachment metadata are stored separately. Android's optional evidence object documents local identity, observed-only time, session order and unknown/possibly clipped completeness.

Coverage values are `complete_observed_range`, `partial`, `gap_detected` or `awaiting_backfill`, accompanied by gap/backfill flags. Complete observed range describes only the declared range successfully observed, never unseen provider history. The current default can overclaim completeness without unreadable-turn evidence; F06 requires carrying those observations and defaulting unknown reading to partial.

The validator permits one to one hundred events per request and a default maximum of 524,288 UTF-8 bytes. Text is nonempty and at most 250,000 characters; conversation IDs are at most 512 characters; titles at most 1,000; sequence is zero to one million; up to fifty HTTPS links and twenty-five attachment metadata objects are allowed. Source URLs for web capture must match the provider host. A non-web event without a URL requires a source locator. UTF-8 byte limits differ from character limits, so clients aim below 450,000 bytes and split requests. Exact validation stays in `backend/src/validation.js`.

### 4.2 Commit order and cross-store failure

The current path authenticates, validates, excludes deleted sources, redacts recognized secrets and hashes the redacted envelope. It writes an immutable R2 archive and then calls a service-only database ingestion function, which commits canonical message/revision/index/cursor changes. R2 paths include workspace/provider/date/batch UUID, and stored hashes reject batch ID reuse with different content.

Postgres transactions protect database changes within their transaction. R2 and Postgres do not form one transaction. The earlier error handler deleted a newly created archive when the metadata call threw, even if the database committed before the response was lost. F08 therefore requires an ownership-first path, immutable commit-status lookup and a durable reconciliation/cleanup record before removing any possible sole archive copy.

The required repair must distinguish “database definitely rejected,” “committed,” and “outcome unknown.” Retrying or repairing unknown outcomes must not reapply messages twice, lose provenance or create an orphan with no accountable cleanup. Fault injection will simulate commit-before-timeout, concurrent retry, archive failure and cleanup failure.

### 4.3 Strict acknowledgement and readback

A client can mark delivery complete only after the response identifies the expected batch, reports success/committed state and accounts for every submitted event. Inserted, updated and duplicate counts must match accepted events; explicit previously-deleted counts are separate terminal outcomes. HTTP 200, HTML, missing JSON, a different batch ID or a partial count remains unconfirmed and retains the request for safe recovery.

Android currently validates explicit acknowledgement fields; imports validate status/count accounting. Extension and macOS accept HTTP success too broadly. Shared conformance fixtures must pin equivalent outcomes across clients without requiring the same implementation language.

A receipt proves a request's declared result; coverage/content readback adds evidence of what is actually stored. Canonical IDs, redacted text digests, roles, ordering and timestamp evidence must be compared for integrity checks. Current import ID/role lookup is insufficient to detect silent shortening or wrong date/order.

Old cleanup work must be restricted to the deleted copy's generation/archive scope so it cannot erase newly ingested data. A second deletion of the same source must create a fresh cleanup obligation instead of inheriting an earlier completed timestamp. Preserve unrelated messages in shared archives. Verify ordinary recapture/import after cleanup, a delayed cleanup overlapping recapture and repeated deletion. The effective live table/functions were inspected and preserved before applying `20261022000045_v1_allow_chat_recapture_after_cleanup.sql`. ## 14. Terms used in this document

**A transcript** is the ordered record of visible user and AI messages. **An adapter** is a provider-specific reader. **The DOM or Accessibility tree** is the structured page/application content available to a permitted reader; it may omit history or complete text.

**A queue** is durable work waiting to upload/process. **A batch** groups a bounded set of events under one request ID. **A receipt or acknowledgement** confirms what that exact request committed. **Idempotency** means safely repeating the same request without applying it twice.

**Canonical identity** identifies the actual chat/turn independently of the device view. **A digest/hash** is a fingerprint of content, not proof that two equal texts are one turn. **Provenance and lineage** record where information came from and the exact source revisions supporting it.

**A migration** is an ordered database change. **RLS** limits database rows by ownership. **A token** is a credential representing an authenticated/granted session; **a scope** names the operation it permits. **A tombstone** is a small deletion marker; a proposed **lifecycle generation** distinguishes an old deleted source state from a new explicitly authorized restoration.

**Redaction** replaces recognized secret values with markers. **Pagination** retrieves a large dataset in complete bounded portions. **Back-pressure** slows new work when capacity is reached while protecting accepted data. **A checkpoint** is a generated summary tied to exact source revisions. **PGlite** is disposable local database testing and does not verify live Supabase Auth or production behavior.

## 16. Completion contracts behind the accepted recommendations

### 16.1 Permission changes, retention and lifecycle state

The final-product client contract includes an owner binding, a durable event/revision store and immutable pending/rejected delivery records. The user explicitly deferred new multi-owner local partitioning for the current single-owner V1; the storage/receipt integrity requirements remain. A local transaction or equivalent single-writer atomic commit persists the event and its outgoing work before acknowledging acceptance. If storage is full or corrupt, the client refuses to advance its read cursor and exposes recovery. A bounded preview cache is separate from protected unsent payloads. Cloud confirmation must be validated before clearing payload text; compact source/message identity, revision digest and receipt information remain for reconciliation. App-level protection and secure credential storage must be verified separately on each client, rather than inferred from the operating system encrypting a disk.

The implementation default preserves same-owner unsent work when a companion is disconnected, while disabling new collection and privileged delivery. The person can deliberately erase device data after a scoped unsent-count warning. A device pause stops future collection; it does not promise cancellation of a batch already accepted by the cloud. A source/account deletion suppresses access and invalidates old upload authorization before cleanup completes. Account-wide/device pause settings have a monotonically increasing settings version and an applied version per registered client; an offline client is pending until its acknowledgement. Reconnection checks current ownership, pause, revocation and deletion state before accepting new observation or replaying work.

The latest V1 lifecycle has an active source, an identified deletion/cleanup operation and a cleanup-completed state that permits ordinary ingestion again. It does not require a separate restore-consent transition. ### 17.3 Parameters and their exact effects

**Time emphasis** is a soft preference among relevant allowed candidates. Relevance remains a minimum requirement; recent unrelated messages cannot replace a highly relevant older source solely because they are new. Compute recency from original source time relative to the fixed task reference date; unknown original time gets a visible unknown/neutral treatment rather than a fabricated current timestamp. A separate explicit date filter, if later included, is a hard exclusion and must not be confused with this weighting control.

**Matching style** is lexical versus conceptual relevance. A later hybrid engine can retrieve both lexical and vector candidates, normalize or rank-fuse their contributions and expose a bounded mixing preference. It must use the same underlying indexes in both conditions and record changes in candidate recall as well as reranking. It cannot modify ChatGPT’s, Claude’s or Gemini’s private retrieval weights. The first prototype can omit/disable this control if no verified semantic index is ready; a smaller honest demonstration is acceptable.

**Evidence breadth** controls redundancy versus variety within the relevant candidates. A focused setting can keep nearby complementary passages; a varied setting penalizes redundant passages and rewards distinct relevant evidence. Maximal Marginal Relevance is a candidate mechanism for trading query relevance against redundancy, rather than proof that variety always improves an answer. [Carbonell and Goldstein’s original MMR paper](https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf). Use a minimum relevance floor, deterministic tie-breaks and source-lineage preservation; repeated wording in different sources is not permission to erase either original message.

**Packing amount and granularity** define how much source text reaches the model and whether a passage includes adjacent turns. Start from original excerpts and deliberate notes, preserve speaker/order, and mark clipped passages. Both study conditions share a maximum, initially within the current 10,000-character default unless the reviewed protocol sets another value. A character budget is not a token budget. A detail control, source weighting, confidence threshold, query expansion or more elaborate passage chunking may be useful later, but the first prototype should not expose a dashboard of unexplained algorithm coefficients. Recency, explicit origin and frequency are evidence features, not truth guarantees.
